## 编译和启动

使用系统 Python 和系统 OpenCV；先退出 Conda 环境。

```bash
cd /home/szx/nav/odin_0915
source /opt/ros/humble/setup.bash
source install/local_setup.bash
CMAKE_BUILD_PARALLEL_LEVEL=2 /usr/bin/colcon build --symlink-install \
  --packages-select odin_ros_driver sensor_scan_generation terrain_analysis terrain_analysis_ext pb2025_nav_bringup --parallel-workers 1 \
  --cmake-args -DOpenCV_DIR=/usr/lib/x86_64-linux-gnu/cmake/opencv4 \
  -DPython3_EXECUTABLE=/usr/bin/python3 -DPYTHON_EXECUTABLE=/usr/bin/python3
source install/setup.bash
export LD_LIBRARY_PATH=/usr/lib/x86_64-linux-gnu:${LD_LIBRARY_PATH}
export ODIN_CALIB_DIR=/home/szx/nav/odin_0915/runtime
ros2 launch pb2025_nav_bringup rm_navigation_reality_launch.py \
  world:=0922 slam:=False use_robot_state_pub:=True
```

本次已将驱动和必要启动配置编译到原来的 `build/install/log`。
上次迁移生成的 `build_v0144/install_v0144/log_v0144` 不再使用；不要 source 那套覆盖层。
Nav2 默认使用独立进程，仍可显式指定 `use_composition:=True`。机器人描述开关沿用原值，
单独启动导航时显式指定 `use_robot_state_pub:=True`。不要同时启动两套雷达驱动。

默认驱动配置是 `config/control_command.yaml`，也可直接指定：

```bash
ros2 run odin_ros_driver host_sdk_sample --ros-args -p config_file:=/绝对路径/配置.yaml
```

## 驱动内部兼容

- `navigation_compatibility: 1` 只针对 ROS 2。保留旧导航订阅的
  `/odin1/odometry`、`/odin1/odometry_highfreq`，子坐标系为 `odin1_base_link`。
- 新版 SDK 原始位姿的参考点是 IMU。驱动读取设备 WIWC 中的实际
  `T^imu_lidar`，使用 `T^odom_lidar = T^odom_imu × T^imu_lidar` 转换完整位姿。
  原始数据另发到 `/odin1/odometry_imu`、`/odin1/odometry_highfreq_imu`。
- 实机在线标定包含非零旋转，平移也与官网名义值不同；不使用名义值硬套这台设备。
  没收到有效 WIWC 时，仅发布原始位姿，暂不发布导航兼容位姿。
- 两路兼容里程计分别按消息时间计算速度，在输出子坐标系表达，包含杆臂影响。
  首帧、超过 1 秒的间隔填零；丢弃倒退时间。SDK covariance 数组被用于承载
  外参，兼容话题清空这些数组，避免把它们当统计协方差；原始话题保留 SDK 数据。
- 车体到 `odin1_base_link` 的安装值沿用旧模型：`chassis` 下
  `(0.1, 0, 0.35)m`，旋转为零。这是保留原安装标定，没有重新测量安装点。
  模型 visual 的 `-π/2` 局部旋转也沿用原值。
- 驱动增加 `odin1_base_link→lidar` 单位静态 TF，并按 WIWC 在线标定发布
  `lidar→imu`。原始点云仍属于 `lidar`，IMU 数据仍属于 `imu`。
- 沿用 0906 的 `map→odom` 发布方向，对 SDK 变换整体求逆。
  关闭厂商的 `send_odom_baselink_tf` 和额外 TF 补发；
  `odom→base_footprint` 继续由原导航节点负责。

```text
map → odom → base_footprint → chassis → odin1_base_link → lidar → imu
```

`/odin1/cloud_slam` 保持 odom 系 XYZRGB，原有 `odin_cloud_to_xyzi` 源码不变。
`save_pcd.sh` 只修改订阅 QoS 以接收新版的 best-effort 点云。

默认仍优先使用 9 月地图：
`map/20260922_110931/map_20260922_111050.bin`，相对驱动包 share 目录解析。
配套二维地图仍是导航包中的 `map/reality/0922.yaml`。
地图在启动前检查是否存在；标定、日志和录制写入可写运行目录。新地图默认保存到驱动源码的 `map/{driver_start_time}/`，不使用 `.ros`；可通过 `mapping_result_dest_dir` 覆盖。

旧地图已成功传输，但最终使用默认配置复测 40 秒，仅有约 0.5Hz 的 IMU 和
0.43Hz 的原始点云，没有里程计和 map→odom；先前启用算法重置也未恢复。
纯里程计模式和今天的地图可正常运行，今天地图还明确返回了
`relocalization success!`。用户随后确认当前不在旧地图对应的场地，旧地图的重定位可用性需回到原场地验证，
不能把“SDK 地图下发成功”视为已完成旧地图导航迁移。
当前测试不能判定旧地图损坏或格式不兼容。

今天地图仅用于驱动对照测试，未作为旧二维导航地图的配套定位地图。

自主行驶或导航精度。

对照测试已经验证：IMU 约 400Hz，普通里程计和 SLAM 点云约 10Hz，
高频里程计约 400Hz；旧点云适配、sensor_scan、TF 单父节点与无环检查通过。
PCD 脚本实机累积 36 帧，输出 4640 个降采样点。
位姿与速度转换的编译测试覆盖完整旋转、杆臂、双流独立、无效外参和时间倒退。

## 本轮授权的导航修复与退出检查

驱动以外修改五个源码文件：sensor_scan_generation 的源文件/头文件、两套地形节点源文件、
rm_navigation_reality_launch.py。具体内容：

- sensor_scan 检查输入坐标系，TF 不可用时跳帧，最多等待 0.2 秒；按消息时间计算子帧速度，
  首帧/长间隔填零，跨 ±π 使用短旋转；历史数据改为实例成员。
- 两套地形节点复用执行器并检查 ROS 状态，修复退出异常；里程计订阅采用 SensorDataQoS，
  接收新版 best-effort 输出，避免只有点云却收不到位姿。
- Nav2 默认使用独立进程，避免组合容器退出卡住；保留地图默认 0922 和系统 OpenCV 优先加载。
- 雷达驱动信号处理只置标志，由主线程清理 SDK，解决在 SDK 回调线程内停流时可能卡死的问题。

编译通过。离线检查覆盖 TF 缺失、坐标错误、局部点云、速度时间基准与旋转边界，全部通过。
实机采样：IMU 397.11Hz，高频里程计 393.78Hz，普通里程计约 10.25Hz，
sensor_scan 和两套地形输出约 10.21Hz；点云 XYZ/RGB 位模式保持一致，TF 无父节点冲突和环。
相同时间戳原生/兼容位姿与传感器 TF 一致。最终 20 秒采样未捕获 map→odom，
不能把该采样当作全局定位 TF 持续可用的证明；旧图定位和对齐需回原场地验证。

统一 launch 实机测试未显式指定 use_composition，确认默认 Nav2 独立进程运行；
测试使用 autostart=False、不下发目标，20 个进程全部正常退出，没有超时强杀。

机器人模型、odin_nav_tools 源码、包依赖、原 AGENTS.md、原 readme.txt 保持原版。
没有独立里程计适配节点，没有新增工作区操作脚本，继续使用原 build/install/log 和原启动命令。
